# ADR-0009: Security

Status: Proposed

## Context
- The app is internet-facing. `src/000.js` runs `exec('bin/004 ' + JSON.stringify(req.headers))` (also `bin/005`, `bin/006`).
- **Injection mechanics:** the JSON string is concatenated unquoted, so the shell sees JSON's double quotes as shell quotes. Inside them `$(...)` and backticks are still expanded, and a header `"` becomes `\"`, which is a literal in shell double quotes. So the exploitable vectors are command substitution (`$(...)`, backticks) in header names or values, not a bare `'`. **Confirmed locally on 2026-10-20:** a request header `X-Probe: $(touch /tmp/quest-inj)` created the file, even though the binary itself could not run on macOS. The shell runs before the binary is involved.
- The app is vendor-supplied and scored by its behavior.
- `SECRET_WORD` is a quest value, not a real credential, but it should still be handled as configuration, not code.
- TLS uses a self-signed cert (ADR-0003).
- No `.gitignore` exists yet (ADR-0004).

## Decision
1. **Do not modify the vendor app's behavior.** Contain the risk instead.
2. **Network:** tasks accept traffic only from the ALB security group; the ALB exposes 80 (redirect) and 443 only. Task egress is **not** restricted at first: `bin/001`, `bin/002`, and `bin/004` embed `net/http` clients, and `001`/`002` use IMDSv2 over plain HTTP, so I do not yet know which outbound calls they make. Observe on the first deploy, then tighten egress to what is actually used (at minimum 443 for ECR and logs).
3. **Container:** non-root user, `readOnlyRootFilesystem` where the app tolerates it, no extra Linux capabilities, a pinned supported base image (digest if practical), and ECR image scan on push.
4. **IAM:**
   - **Task execution role:** only the AWS-managed `AmazonECSTaskExecutionRolePolicy`, and no task role, since no AWS API calls were observed in the app source. The binaries' cloud detection uses metadata endpoints; whether it needs IAM is untested.
   - **Deployer identity (done 2026-10-20):** root is not used for deploys. `infra/aws/bootstrap/bootstrap.sh` creates the IAM user `quest-deployer` with the customer-managed policy `QuestDeployer` (`infra/aws/bootstrap/quest-deployer-policy.json`) plus AWS's `SignInLocalDevelopmentAccess` so `aws login` works. The policy:
     - allows `ec2`, `ecs`, `ecr`, `elasticloadbalancing`, `acm`, `logs`, `autoscaling`, and `tag` only when `aws:RequestedRegion` is `us-east-1`;
     - limits IAM to roles and instance profiles named `quest-*`, allows `AttachRolePolicy` only for `AmazonECSTaskExecutionRolePolicy` and `AmazonEC2ContainerServiceforEC2Role`, and `PassRole` only to `ecs-tasks` and `ec2`;
     - allows creating only the ECS, ELB and Auto Scaling service-linked roles, and budgets named `quest-*`;
     - explicitly denies user, access-key, inline-policy, policy-creation, permissions-boundary, `organizations:*` and `account:*` actions.
   - Verified with Access Analyzer policy validation (no findings) and 27 IAM-simulator checks (13 allowed, 14 refused, including attaching `AdministratorAccess`, passing to Lambda, modifying an existing CDK role, and other regions). The simulator does not prove Terraform has every permission it needs.
5. **TLS:** ALB policy `ELBSecurityPolicy-TLS13-1-2-2021-06` (name from memory; confirm with `terraform validate`/`plan`); HTTP redirects to HTTPS.
6. **Secrets:** `secret_word` is a `sensitive` Terraform variable, passed via `TF_VAR_secret_word` or a gitignored tfvars. **Create `.gitignore` (`*.tfvars`, `*.tfstate*`, `.terraform/`, `node_modules/`) before `terraform init`.** The task definition carries the word as a plain env var because the quest requires one.
7. **No private keys in git:** the self-signed key is generated by Terraform and lives only in state.
8. **Credentials:** `aws login` sessions are short-lived (up to 12 hours). No long-lived access keys are created for `quest-deployer` (the policy denies `iam:CreateAccessKey`).

## Alternatives considered
| Option | Why not |
|---|---|
| Patch `src/000.js` to use `execFile` with an argument array | Fixes the injection properly, but alters the supplied app. Listed as the first improvement. |
| WAF in front of the ALB | Cost and complexity (~$5/mo plus rules) beyond demo scope; mention in "Given more time". |
| Secrets Manager / SSM SecureString for `SECRET_WORD` | Better practice; the value may be visible on the public index page, so low benefit here. Worth it for real secrets. |
| Private subnets | See ADR-0003; cost tradeoff. |

## Tradeoffs
- (+) Defense in depth with no changes to scored behavior and little cost.
- (-) The injection flaw remains in the app; only its blast radius is reduced.
- (-) Terraform state contains the private key and the secret word in plaintext.

## Risks
1. Command injection via headers gives code execution inside the container.
2. State file or tfvars leak exposes the key and secret word (no `.gitignore` yet).
3. Self-signed cert trains users to click through warnings; no MITM protection for clients that skip verification.
4. Public IPs on tasks, if the SG is ever loosened.
5. Read-only root filesystem breaks the app (it may write temp files).
6. Removing the task IAM role breaks cloud detection if it needs IAM.
7. Restricting egress before observing the binaries breaks cloud detection or the checks.
8. `ec2:*` in `us-east-1` is broad: if the deployer session were stolen it could launch many instances (cost, abuse).
9. The policy may be missing an action Terraform needs, so `plan` or `apply` fails with AccessDenied.

## Mitigations
1. Non-root, dropped capabilities, egress tightened once the binaries' outbound calls are known, no task IAM role, and short lifetime (ADR-0007) limit the damage. Document the flaw and its fix in `SOLUTION.md`. The mechanism is confirmed locally; do not probe the public deployment.
2. `.gitignore` first. Local state stays on the operator machine; for anything beyond the demo use an encrypted S3 backend with locking.
3. Use ACM with a real domain in production (after checking the `/loadbalanced` Host question in ADR-0003).
4. Verify by requesting the task public IP directly and expecting a timeout.
5. Test with the read-only flag locally; drop it and record the reason if the app fails.
6. Check `/aws` and `/` output on the first deploy; add a minimal task role only if needed.
7. Start with open egress, record outbound connections on the first deploy (for example with VPC flow logs), then tighten and re-run `tests/smoke.sh`. Roll back any rule that changes a check result.
8. Console password plus MFA on the `quest-deployer` user, short sessions, a billing Budget alert (ADR-0008), and teardown after review (ADR-0007). Tighten `ec2:*` to the actions actually used if time allows.
9. Widen the policy minimally for any AccessDenied seen, re-run the bootstrap script, and record the change here. Do not fall back to root.
