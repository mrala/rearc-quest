# ADR-0004: CI/CD

Status: Accepted (2026-10-20). Partly implemented: the Makefile and SHA tags exist and work; the pull-request workflow was not written.

## Context
- The working tree is a clone of the upstream challenge repo: `origin` is `https://github.com/rearc/quest.git` and the log is upstream's history. We cannot push there, and the README asks that solutions not be shared publicly.
- `.gitignore` and `package-lock.json` exist and are committed.
- The deployment is a one-off demo that may be torn down within a week.
- The dev machine is Apple Silicon. Docker, Terraform and the AWS CLI are installed. The default `aws login` profile is the root user and the region is `us-east-1`; deploys use the scoped `quest-deployer` user instead (ADR-0009). The image must be `linux/amd64`.

## Decision
- **Prerequisites before any build or apply:**
  1. Create a **private** repo for the submission and point `origin` at it (keep upstream as `upstream` if wanted).
  2. Add `.gitignore` covering `node_modules/`, `.terraform/`, `*.tfstate*`, and `*.tfvars`.
  3. Run `npm install` and commit `package-lock.json`. Dockerfile uses `npm ci` only after the lockfile exists.
  4. Create the scoped deployer with `infra/aws/bootstrap/bootstrap.sh` (admin credentials, one time), set its console password and MFA, then `aws login --profile quest-deployer --region us-east-1`. All Terraform and Makefile commands use `AWS_PROFILE=quest-deployer`.
  5. Pin the Terraform AWS provider to `>= 6.23.0`, the first version where provider auth works with `aws login` credentials (hashicorp/terraform-provider-aws#45316). Use **local state**: when that issue was discussed, the S3 backend did not accept `aws login` credentials (tracked in hashicorp/terraform#37976; current status not checked). If an S3 backend is added later, use the `credential_process` workaround with `aws configure export-credentials`.
  6. Keep the vendor `README.md` intact and write the submission docs in `SOLUTION.md`, linked from the top of `README.md`.
- **Manual, scripted deploy** via a `Makefile` with targets: `build`, `push`, `plan`, `apply`, `smoke`, `destroy`. The image is built with `docker buildx build --platform linux/amd64` and tagged with the git short SHA (not `latest`), and the tag is passed to Terraform as `image_tag`.
- **Not built:** a GitHub Actions workflow on pull request that would run `terraform fmt -check`, `terraform validate`, a `docker build`, and a local container smoke test of the six routes, without applying. The same checks exist as commands (`make -C infra/aws fmt validate`, `make smoke-local`) and are run by hand.
- Apply stays a human action.

## Alternatives considered
| Option | Why not |
|---|---|
| Full GitHub Actions deploy with OIDC to AWS | The right production choice; adds IAM trust setup and repo secrets for a demo that may live a week. |
| CodePipeline/CodeBuild | More AWS resources to define and tear down; no gain at this scale. |
| Build in CodeBuild to avoid local Docker | Reasonable fallback if local amd64 builds are too slow. |
| Click-ops / ad hoc CLI | Not reproducible; the quest asks for IaC. |

## Tradeoffs
- (+) Minimal moving parts; the same commands run locally and in CI.
- (+) SHA tags give rollback and an audit trail.
- (-) No automated deploy; the demo depends on one operator's credentials.
- (-) Emulated amd64 builds on arm64 are slow.
- (-) Nothing checks changes automatically, because the workflow was not written.

## Risks
1. Solution pushed to a public location, or to the wrong remote.
2. Local state or credentials drift between operators.
3. Wrong tag deployed, or `latest` silently changes.
4. Secrets leak into CI logs or the repo (`SECRET_WORD`, AWS keys).
5. Expired AWS session mid-apply leaves partial state.

## Mitigations
1. Create the private repo first; check `git remote -v` before the first push.
2. Single operator and local state (see Decision 5); remote state in S3 with locking is listed as a future improvement in the README, with the `aws login` caveat above.
3. Terraform takes an explicit `image_tag`; never use `latest`.
4. No AWS keys are used in CI (there is no CI; a future pull-request workflow would need none). Pass `SECRET_WORD` via `TF_VAR_*` or a gitignored tfvars file. Create `.gitignore` before `terraform init`.
5. Run `aws sts get-caller-identity` before `apply`; rerun `apply` to converge if interrupted.
